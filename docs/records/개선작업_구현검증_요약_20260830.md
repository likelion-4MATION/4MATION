## 1. 결론

초기에 정한 5개 기능 범위는 모두 구현·검증됐다.

| 번호 | 계획 | 상태 | 확인 결과 |
|---:|---|---|---|
| 1 | Q-Form 조건에 맞는 첨부 반환 파이프라인 확인 | 완료 | 실제 로컬 검색 → `chain` → 첨부 실파일 반환 통과 |
| 2 | 멀티턴 Q-Form 값을 검색 질의에 반영 | 완료 | 고정 `field: value` 확장, 원 질의와 검색 질의 분리, 기본 ON |
| 3 | 동적 답변 검증 게이트 | 완료 | 경고·재생성·차단, 규칙별 토글, 다음 생성 요청부터 반영 |
| 4 | 검색 `top-k` 기본값 5와 관리자 조정 | 완료 | 기본 5청크, 관리자 `1~5`, 다음 생성 요청부터 반영 |
| 5 | 관리자 챗봇 모델 선택 | 완료 | HCX·DeepSeek·Upstage 전환 및 세 공급자 최소 라이브 호출 HTTP 200 |

여기서 “완료”는 합의한 기능 인수 범위를 뜻한다. 모델별 전체 RAG 품질·지연·비용 벤치마크와
운영 경계값 보정은 별도 후속 작업이다.

## 2. 현재 답변 흐름

```text
사용자 원문
  → 업무/OOS 라우팅
  → Q-Form 슬롯 추출·멀티턴 이월
  → 검색용 확장 질의 생성(field: value)
  → hybrid_bf 검색(기본 5청크)
  → 선택된 LLM으로 답변 생성
  → URL·출처·수치 검증 게이트
  → Q-Form 조합에 맞는 첨부 필터
  → 답변·출처·첨부·검증 메타 반환
```

원문과 검색문은 역할이 다르다.

- 분류와 답변 생성: 사용자가 입력한 원문 사용
- 검색과 검색 유사도: 원문 뒤에 Q-Form 슬롯을 붙인 확장 질의 사용
- 첨부: 검색된 청크에서 후보를 만든 뒤 Q-Form 조합으로 후단 필터

이 분리 때문에 검색 재현율을 높이면서도 모델이 내부 슬롯 표기를 사용자 질문처럼 답하는 것을
막을 수 있다.

## 3. Q-Form 검색 확장

확장 형식은 순서와 필드명이 고정돼 있다. 값이 없는 필드는 생략하고 줄바꿈 등은 한 줄로
정규화한다.

```text
[QFORM]
party: 송금인
sub_task: 반환신청
qualification: 대리인
subject: 미성년자
method: 방문
```

예시는 다음처럼 조립된다.

```text
미성년자 대신 착오송금 반환을 신청하려면?

[QFORM]
party: 송금인
sub_task: 반환신청
qualification: 대리인
subject: 미성년자
```

주요 구현 파일:

- `chatbot/qform_state.py`: 슬롯 직렬화
- `chatbot/qform_flow.py`: 원문과 검색문 분리
- `chatbot/orchestrator.py`: 확장 질의를 답변 체인으로 전달
- `chatbot/chain.py`: 검색에만 `retrieval_query` 사용
- `tests/test_qform_boost.py`: 형식·전달·프롬프트 분리 회귀 테스트

## 4. 첨부 반환

첨부는 정답셋 점수로 평가하지 않았다. 요청한 확인 범위는 코드와 실제 로컬 데이터에서
파이프라인이 이어지는지였고, 다음 경로가 통과했다.

```text
실제 Searcher hits
  → chain.answer_in_scope(..., qform=...)
  → attachments.collect(hits, qform=...)
  → 조합 일치 첨부 메타
  → 로컬 실파일 존재 확인
```

검증 명령:

```bash
python chatbot/verify_qform_search_attachments.py
python chatbot/verify_qform_integration.py
python chatbot/verify_qform_multiturn.py
```

`attachments`는 기존 4필드 답변 계약을 줄이지 않고 추가된 부가 필드다. 검색 결과에 첨부가
없거나 Q-Form 조합에 맞는 파일이 없으면 빈 배열을 반환한다.

## 5. 답변 검증 게이트

검증 규칙은 LLM을 추가 호출하지 않는 결정론 검사다.

| 설정 | 기본값 | 의미 |
|---|---:|---|
| `answerChecksEnabled` | `true` | 전체 검증 사용 |
| `answerGateMode` | `warn` | 실패 답변을 유지하고 경고 메타 기록 |
| `answerGateMaxRetries` | `1` | 재생성 모드의 추가 생성 횟수 |
| `checkUrls` | `true` | 근거 밖 URL 검사 |
| `checkCitations` | `true` | `[출처N]` 누락·범위 검사 |
| `checkNumbers` | `true` | 근거 밖 금액·비율·전화번호 검사 |
| `strictUrl` | `true` | 출처 목록 기준으로 URL을 엄격하게 검사 |

실패 처리 모드:

- `warn`: 생성 답변은 유지하고 `checks.gate.action=warned` 기록
- `regenerate`: 실패 이유를 넣어 답변을 다시 생성하고 재검사
- `block`: 실패 답변을 고정 안내 문구로 교체

소관 밖 고정 거절문은 모델 생성물이 아니므로 검색·생성·검증을 생략한다. `regenerate`만 추가
LLM 호출이 발생하며, 관리자 예상 지표는 실패율 실측 전까지 모든 RAG 답변이 재생성된다는
최악 조건의 상한이다.

주요 구현 파일:

- `chatbot/answer_checks.py`
- `chatbot/chain.py`
- `admin/registry.py`
- `admin/settings.py`
- `tests/test_answer_gate.py`

## 6. 검색 문맥 수 `k`

- 코드 기본값: `chatbot.chain.CONTEXT_K = 5`
- 관리자 기본값: `5`
- 관리자 허용 범위: `1~5`
- 반영 시점: 저장 후 사용자 서비스의 다음 생성 요청

중요하게, `k=5`는 서로 다른 원문 문서 5개가 아니라 검색 청크 5개다. 같은 문서의 여러 청크가
선택되면 중복 제거된 출처 문서 수는 5보다 작을 수 있다. 실제 점검에서는 5청크가 4개 원문
문서로 구성됐다.

함수 인자의 기본값은 `5`로 고정하지 않고 `None`으로 두며, 호출 시점에 `CONTEXT_K`를 읽는다.
그래야 관리자 변경이 프로세스 재시작 없이 다음 질의부터 적용된다. 진단 도구가 명시적으로
`k=10` 등을 넘기는 경로는 계속 허용한다.

## 7. 챗봇 모델 전환

관리자 `챗봇 모델` 선택지는 다음 세 개다.

| 관리자 값 | 표시 | 기본 모델 환경변수 | 라이브 최소 호출 |
|---|---|---|---|
| `hcx` | HyperCLOVA X | `CLOVA_MODEL=HCX-003` | HTTP 200 |
| `deepseek` | DeepSeek | `DEEPSEEK_MODEL=deepseek-v4-flash` | HTTP 200 |
| `upstage` | Upstage Solar | `UPSTAGE_MODEL=solar-pro3` | HTTP 200 |

관리자 저장값에는 공급자 선택만 들어간다. API 키·주소·실제 모델명은 `.env`에만 있고
`admin/data/admin_config.json`이나 응답 로그에는 저장하지 않는다. `.env`는 Git ignore 대상이다.

```ini
DEEPSEEK_API_KEY=
DEEPSEEK_API_URL=https://api.deepseek.com/chat/completions
DEEPSEEK_MODEL=deepseek-v4-flash

UPSTAGE_API_KEY=
UPSTAGE_API_URL=https://api.upstage.ai/v1/chat/completions
UPSTAGE_MODEL=solar-pro3

CLOVA_API_KEY=
CLOVA_API_URL=
CLOVA_MODEL=HCX-003
```

전환 시 `LLM_PROVIDER`와 `MODEL_NAME`을 함께 바꾼다. 분류와 답변 생성은 모두 같은 선택값을
사용하며, 사용자 오류 신고의 `model_version`에도 실제 선택 모델명이 기록된다.

공급자별 차이는 요청 어댑터에서 처리한다.

- HCX: camelCase 생성 파라미터와 요청 ID 헤더 사용
- DeepSeek: OpenAI 호환 요청과 `thinking`·JSON 출력 옵션 사용
- Upstage: OpenAI 호환 요청을 사용하되 DeepSeek 전용 `thinking`과 `response_format`은 제거

DeepSeek와 Upstage의 응답시간·비용은 아직 서비스 실측 근거가 없으므로 관리자 화면에서 HCX
수치를 재사용하지 않고 `미측정`으로 표시한다.

## 8. 관리자 런타임 반영

```text
관리자 저장
  → admin/data/admin_config.json 원자적 교체
  → 사용자 서비스가 파일 revision 감지
  → settings.apply_runtime()
  → 다음 생성 요청부터 k·검증 게이트·LLM 공급자 반영
```

청킹 설정만 재빌드가 필요하다. 이번 작업의 `k`, 검증 게이트, 모델 선택은 모두 런타임 설정이다.

## 10. 남은 운영 후속 작업

초기 5개 기능의 미완료 항목은 없지만 다음은 운영 품질을 위해 남겨 둔다.

1. **HCX `temperature=0` 경계 보정**  
   관리자 범위는 현재 `0~1`이지만 HCX 라이브 API는 `0`을 HTTP 400으로 거부했다. 기본값
   `0.2`는 정상이다. HCX 선택 시 최소값을 보정하거나 관리자 최솟값을 올려야 한다.

2. **모델별 전체 RAG 스모크**  
   라이브 검증은 공급자 전환과 요청·응답 형식을 확인하는 최소 호출이었다. 각 모델로 실제
   Q-Form 검색 문맥, 출처, 첨부, 검증 게이트까지 한 번에 통과하는 대표 질의를 남기면 운영
   회귀에 더 유용하다.

3. **모델별 품질·지연·비용 측정**  
   동일 질문셋으로 HCX·DeepSeek·Upstage를 비교하지 않았으므로 모델 간 품질 우열과 운영비는
   아직 판단할 수 없다.

4. **답변 검증 규칙 보정**  
   게이트 동작은 검증했지만 실제 운영 답변에서의 오탐·미탐률은 측정하지 않았다. 기본 모드를
   `warn`으로 둔 이유이며, `block` 전환 전에는 표본 검수가 필요하다.
