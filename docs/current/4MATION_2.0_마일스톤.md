# 4MATION 2.0 서비스 고도화 마일스톤

기존 6개 업무를 지원하는 서비스를 먼저 배포하고, 라우팅부터 단계적으로 검증·개선해
지인·동료 등 초대한 소수 사용자가 이용할 수 있게 만든다. 배포 경험을 먼저 쌓고,
각 개선을 테스트·재배포·운영 확인까지 연결한다.

> 합의 기준: 2026-11-07 · 계획 확정, M1 실행 대기

## 목표와 범위

- 첫 이용자: 지인·동료 등 초대한 테스트 사용자. 초기 5~10명은 계획상의 가정이며 모집 인원은 미확정이다.
- 서비스 범위: 기존 6개 업무 전체. 업무별 정상 동작과 업무 간 경계·전환을 함께 검증한다.
- 사용자 흐름: 접속 → 질문 → 필요한 추가 질문 → 답변·출처·첨부 확인 → 피드백.
- 첫 배포: 본인 확인용 비공개 배포. 초대 사용자 운영 준비는 M6에서 검증하고 M7에서 실제 운영한다.
- 개발 원칙: 기존 코드·UI·평가 자산 재사용, 작은 변경, 동일 조건 전후 비교, 기존 팀 구현과 개인 기여 구분.
- 확장 원칙: Agent·외부 도구 연동·다중 서버·별도 벡터 DB는 사용자 문제나 측정된 병목이 확인될 때 검토한다.

배포 환경, 월 운영 예산, 서버 사양, 예상 동시 요청 수와 응답시간 목표는 M1 준비에서 정한다.
서비스 품질 목표는 기준선 측정 후 수치와 평가 조건을 함께 정한다. 달력 일정과 소요 기간은 두지 않는다.

## 진행 순서와 상태

| 단계 | 마일스톤 | 선행 조건 | 현재 상태 |
|---|---|---|---|
| M1 | 첫 배포 성공 | 현재 작업 상태 정리와 최소 실행 확인 | 대기 · 다음 착수 |
| M2 | 반복 가능한 배포 | M1 | 대기 |
| M3 | 전체 라우팅 검증과 개선 | M2 | 대기 |
| M4 | Q-Form과 대화 상태 검증과 개선 | M3 | 대기 |
| M5 | 검색과 답변 품질 검증과 개선 | M4 | 대기 |
| M6 | 초대 사용자 운영 준비 | M5 | 대기 |
| M7 | 소수 사용자 운영과 개선 | M6 | 대기 |

각 단계는 선행 마일스톤의 PR을 `dev`에 병합하고 작업 브랜치를 동기화한 뒤 시작한다.
아래 완료 조건을 충족하면 해당 마일스톤의 PR을 열고 상태를 `검증 완료 · PR 검토 중`으로 바꾼다.
병합 후 `완료`로 바꾸며 PR 링크와 검증 근거를 함께 남긴다. 현재 계획 문서 작성은 M1 완료에 포함하지 않는다.

## M1 첫 배포 성공

**목표:** 현재 전체 서비스를 서버에서 실행하고 외부 접속·로그·재시작을 경험한다.

**구현 범위:**

- 작업 브랜치와 최신 `dev`의 차이, 기존 미커밋 변경의 통합 범위를 확인한다.
- 현행 실행 절차로 최소 동작을 확인하고 모델·검색 인덱스·첨부·환경변수의 준비 방법을 정리한다.
- 실제 메모리 사용과 예산을 바탕으로 배포 환경을 선택한다.
- 사용자 앱은 현재 메모리 세션 구조에 맞춰 단일 프로세스로 시작한다.
- 본인만 접근할 수 있도록 제한하고, 관리자 접근과 API 키를 보호한다.
- 로그 확인, 재시작, 데이터 보존 경로를 정리한다. 기존 서버 누적 호출 한도의 동작도 확인한다.

**완료 조건:**

- [ ] 외부에서 접속해 실제 질문에 대한 답변·출처를 확인한다.
- [ ] 모델·인덱스 누락과 실행 실패 원인을 로그로 확인할 수 있다.
- [ ] 재시작 후 서비스를 다시 사용할 수 있고, 세션 초기화와 보존 데이터의 동작을 설명할 수 있다.
- [ ] 같은 절차를 따라 배포를 재현할 수 있도록 기록한다.

**관련 위치:** `web/`, `chatbot/`, `crawler/`, `admin/`, `SETUP.md`, `docs/current/RUNBOOK.md`.
**증빙:** 실행 구성, 모델·데이터 준비 방법, 배포 기록, 시연, 사용 자원 측정.

라우팅 정확도 전면 개선은 M3에서 진행한다. M1에서는 실제 실행과 접근 보호를 막는 문제부터 해결한다.

## M2 반복 가능한 배포

**목표:** 변경을 검증해 다시 배포하고 문제가 생기면 이전 버전으로 복구한다.

**구현 범위:** 의존성·실행환경 고정, Docker 구성 정리, 핵심 테스트와 CI 연결,
설정·데이터·인덱스 버전 구분, 재배포·복구 절차, 요청 식별자와 기본 지연·오류 기록.
M1에서 만든 실행 구성은 재사용한다. 자동 CD는 운영 편의와 필요에 따라 추가한다.

**완료 조건:**

- [ ] 외부 LLM 호출을 대체한 핵심 테스트가 CI에서 실행되고 실패한 변경을 식별한다.
- [ ] 작은 변경을 배포한 뒤 배포 환경에서 동작을 확인한다.
- [ ] 이전 애플리케이션 버전과 호환되는 설정·데이터·인덱스로 복구하는 절차를 검증한다.
- [ ] 실행 중인 버전과 요청 실패의 위치를 확인할 수 있다.

**관련 위치:** 의존성 파일, 새 Docker·CI 구성, `tests/`, `web/`, 운영 문서.
**증빙:** CI 기록, 재배포·복구 기록, 실행환경 구성, 기본 운영 로그.

## M3 전체 라우팅 검증과 개선

**목표:** 6개 업무와 그 경계를 포함한 라우팅 성능을 측정하고 개선한다.

**구현 범위:** 정상·모호·소관 밖·복합 질문 평가셋, 기대 업무·기대 동작 정의,
업무별·실패 유형별 기준선, 라우팅 수정, 전체 공통 회귀 검증과 재배포.

**완료 조건:**

- [ ] 6개 업무와 주요 업무 간 경계를 포함하고 기대 라우팅을 명시한 평가셋이 있다.
- [ ] 같은 데이터·설정으로 기존 방식과 개선 방식을 비교한다.
- [ ] 오분류와 과도한 거절을 구분하고 남은 실패 유형을 설명한다.
- [ ] 전체 공통 회귀 검증과 배포 환경 확인을 통과한다.

**관련 위치:** `chatbot/router_adapter.py`, `chatbot/orchestrator.py`, `chatbot/query_units.py`,
`crawler/rag.py`, 라우팅 평가·테스트.
**증빙:** 평가셋, 기준선·전후 지표, 실패 분석, 의사결정, PR과 배포 기록.

## M4 Q-Form과 대화 상태 검증과 개선

**목표:** 필요한 조건을 수집해 검색으로 전달하고 업무 전환 시 상태를 올바르게 처리한다.

**구현 범위:** 적용 대상 업무의 추가 질문, 불필요한 되묻기 방지, 조건 수정·건너뛰기·재생성,
후속 질문·복합 용건·업무 전환, 이전 조건의 유지·해제, 검색 조건 전달.

**완료 조건:**

- [ ] 각 대화 시나리오에 기대 질문·상태·검색 조건이 명시돼 있다.
- [ ] 필요한 조건이 검색까지 전달되고 업무 전환 시 무관한 조건이 적용되지 않는다.
- [ ] 수정·건너뛰기·후속 질문을 포함한 여러 턴의 회귀 검증을 통과한다.
- [ ] M3 공통 검증과 배포 환경에서 실제 대화 흐름을 확인한다.

**관련 위치:** `chatbot/qform_*.py`, `chatbot/orchestrator.py`, `web/service.py`, `web/sessions.py`, 테스트.
**증빙:** 상태 흐름 문서, 대화 시나리오, 회귀 테스트, 전후 사례, 재배포 기록.

## M5 검색과 답변 품질 검증과 개선

**목표:** 검색 성능과 생성 답변 품질을 구분해 측정하고 사용자에게 필요한 근거를 제공한다.

**구현 범위:** 기존 450문항 검색 평가 재현, 평가 분모·판정 방식 명시, Q-Form 조건 반영 비교,
답변 근거·출처·첨부·최신성 확인, 근거 부족 처리, 실제 답변 검토와 지연·사용량 측정.

**완료 조건:**

- [ ] 검색 지표마다 평가 대상·제외 문항·판정 방식·데이터와 설정 버전을 기록한다.
- [ ] 검색 점수를 답변 정답률로 사용하지 않고 실제 답변 품질을 별도로 평가한다.
- [ ] 같은 조건의 전후 비교와 대표 성공·실패 사례가 있다.
- [ ] 라우팅·Q-Form 공통 회귀 검증과 배포 환경 확인을 통과한다.

**관련 위치:** `crawler/rag.py`, `crawler/eval.py`, 평가 데이터, `chatbot/chain.py`,
`chatbot/answer_checks.py`, 첨부·최신성 가드 경로.
**증빙:** 재현 가능한 평가 결과, 답변 검토, 실패 분석, 품질·지연·사용량 비교.

## M6 초대 사용자 운영 준비

**목표:** 여러 초대 사용자가 서비스를 이용할 때 접근·사용량·실패·피드백을 관리한다.

**구현 범위:** 초대 접근 제한, 관리자 분리, 사용자별·기간별 사용량 제한,
서버 누적 호출 제한 개선, 동시 요청의 대기·시간 초과·재시도, 세션 만료 안내,
오류율·응답시간·토큰 사용량과 비용 추정, 답변별 도움 여부·실패 이유 수집.
피드백 보관 범위와 개인정보 처리도 정리한다.

**완료 조건:**

- [ ] 합의한 동시 이용 수준에서 사용자별 대화·조건이 분리된다.
- [ ] 대기·한도 초과·모델 실패·세션 만료 상황에서 사용자에게 대응 방법을 안내한다.
- [ ] 요청별 실패 원인과 지연·사용량을 확인할 수 있다.
- [ ] 관리자 접근이 제한되고 피드백을 필요한 범위로 수집·조회할 수 있다.
- [ ] M1에서 만든 배포·보존 방식과 M2 복구 절차가 운영 준비 변경 이후에도 동작한다.

**관련 위치:** `web/`, `chatbot/chain.py`, `admin/oos_store.py`, 운영·접근 구성, 테스트.
**증빙:** 동시 사용·장애 검증, 접근·사용량 제한 기록, 운영 지표, 피드백 화면과 보관 정책.

## M7 소수 사용자 운영과 개선

**목표:** 초대한 지인·동료의 실제 사용을 바탕으로 문제를 수정하고 다시 검증한다.

**구현 범위:** 대표 시나리오 테스트와 자유 질문, 6개 업무 및 경계 사례의 전체 커버리지 확인,
도움 여부·이탈·불편·실패 분석, 우선 문제 수정과 재배포, 결과와 개인 기여 정리.

**완료 조건:**

- [ ] 실제 초대 사용자의 사용 결과와 피드백을 수집한다.
- [ ] 우선 문제를 한 차례 이상 수정·재배포하고 개선 여부를 확인한다.
- [ ] 품질·안정성·사용성의 성과와 남은 한계를 근거와 함께 설명한다.
- [ ] 기존 팀 구현과 이번 개인 기여, 주요 기술 선택, 테스트·배포·평가·운영 증빙을 연결한다.

**관련 위치:** 사용자·관리자 서비스, 평가·테스트, 운영 기록, README와 시연 자료.
**증빙:** 개인정보를 제거한 피드백 요약, 개선 전후 결과, PR 이력, 시스템 설명과 시연.

## 브랜치와 마일스톤 PR

- 작업 브랜치: `ukkhnn`. 통합 브랜치와 PR base: `dev`.
- M1 착수 전에는 기존 Q-Form 개선과 고도화 계획을 통합하는 준비 PR을 먼저 제출한다.
  준비 PR의 병합은 M1 완료와 구분하며, 이후부터 마일스톤별 종료 PR을 사용한다.
- 마일스톤별 변경을 작은 커밋으로 기록하고, 종료 조건과 검증 근거를 갖춘 시점에
  `ukkhnn → dev` PR 하나로 제출한다. 계획 작성만으로 M1 PR을 열지 않는다.
- 이미 같은 마일스톤 PR이 열려 있으면 그 PR을 갱신한다. 다른 마일스톤 변경을 같은 PR에 섞지 않는다.
- PR 제목은 `[M1] 본인 확인용 서비스 첫 배포`처럼 단계와 결과를 드러낸다.
- PR 본문에는 해결한 문제, 구현 범위, 완료 조건별 근거, 테스트·배포 결과,
  남은 한계, 복구 방법과 개인 기여를 적는다. 실행하지 않은 검증을 통과로 표시하지 않는다.
- PR 작성과 병합은 구분한다. 자동으로 `dev`에 병합하거나 직접 push하지 않는다.
- `ukkhnn`을 계속 사용하므로 기본 병합 방식은 커밋 이력을 유지하는 merge commit으로 한다.
  저장소 정책이 squash/rebase를 요구하면 다음 작업 전 `dev`를 비파괴적으로 병합하고
  PR diff에 이전 마일스톤 변경이 다시 나타나지 않는지 확인한다.
- PR 병합 후 `ukkhnn` 브랜치를 유지하고 최신 `dev`를 반영한 뒤 다음 마일스톤을 시작한다.
  사용자 작업이 남아 있으면 무조건적인 reset·강제 push·자동 stash를 사용하지 않는다.
- 작업 시작 시 기존 미커밋 변경을 확인한다. 기존 변경은 이번 작업과 구분하고
  필요한 파일만 명시적으로 stage·commit한다.

## 문서와 로컬 메모리 관리

공유할 목표·범위·마일스톤·완료 증빙은 이 문서와 `docs/`에 남긴다.
실행 명령은 [RUNBOOK](./RUNBOOK.md), 설치는 [SETUP](../../SETUP.md)을 갱신해 중복을 줄인다.

`.cowork/`는 Git에서 제외한 로컬 인수인계 공간이다. 현재 상태·결정 이유·다음 작업·세션 기록을
관리하며, 비밀값·개인정보·API 응답 원문은 저장하지 않는다. 공유할 확정 내용은 저장소 문서에
옮기고 링크로 연결한다. `.cowork/`가 없어도 이 문서에서 목표와 진행 방식을 복원할 수 있어야 한다.
구체적인 읽기·갱신 순서는 [AGENTS.md](../../AGENTS.md)를 따른다.
